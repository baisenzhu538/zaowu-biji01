# 造物笔记网站 · 技术栈方案

> 编制依据：`90.需求：MVP最小需求清单.md`
> 选型原则：**尽量轻**。在满足需求的前提下，用最少的技术、最少的依赖、最低的学习成本。
> 编制日期：2026-09-26

---

## 一、选型约束（从需求推导）

技术栈不是拍脑袋选的，先看需求给出了哪些硬约束：

| 需求事实 | 对选型的约束 |
|---|---|
| 50+ 个名词独立页 + 3 个 Wiki 长页 | 内容驱动，**应以静态生成为主**，不需要服务端渲染 |
| 3 个 Wiki 页面"不做折叠，一页到底" | 单页内容量大（源文档 700+ 行），需考虑首屏体积 |
| 名词内容页结构高度一致（同 4 字段） | 数据驱动模板，**不应手写 50 个 HTML** |
| 首页搜索 + 50 词检索 | 数据量极小（50 条），**客户端搜索足够**，不需要搜索服务 |
| 文档提到"后端数据库""LLM 在线检索" | 需满足，但需求量级低，**不值得上重型后端** |
| 目标用户是新手，且是"官方示例案例" | **技术栈本身要简单到能当教材**，不能选复杂方案 |
| 侧边栏 TOC + IntersectionObserver 高亮 | 需要少量前端交互，**但不是 SPA 级复杂度** |
| 移动端适配（TOC 折叠为顶部下拉） | 需要响应式 CSS |
| 三人以下维护、无并发压力 | 不需要考虑集群、CDN 之外的架构 |

**一句话结论**：这是一个**内容型静态网站 + 轻量数据接口**，不是 Web 应用。

## 二、推荐技术栈总览

```
┌─────────────────────────────────────────────────┐
│  内容层    Markdown + Frontmatter（现有素材）    │
├─────────────────────────────────────────────────┤
│  构建层    VitePress（静态站点生成）             │
├─────────────────────────────────────────────────┤
│  交互层    原生 JS / Vue 3（VitePress 内置）     │
├─────────────────────────────────────────────────┤
│  样式层    CSS 变量 + 原生 CSS（不引组件库）     │
├─────────────────────────────────────────────────┤
│  数据层    JSON 文件（词库数据）                 │
├─────────────────────────────────────────────────┤
│  后端层    可选：Cloudflare Workers / Vercel Fn  │
├─────────────────────────────────────────────────┤
│  部署层    GitHub Pages / Vercel（免费）         │
└─────────────────────────────────────────────────┘
```

### 2.1 前端技术栈

| 层 | 选型 | 版本 | 理由 |
|---|---|---|---|
| **构建工具** | **VitePress** | 1.x | 见下方专项说明 |
| **UI 框架** | Vue 3（VitePress 内置，按需使用） | 3.4+ | 只在需要交互的组件里用，不写 SPA |
| **样式** | **原生 CSS + CSS 变量** | — | 需求里的设计参数（色值、间距、圆角）用变量管理，**不引 UI 组件库** |
| **字体** | Manrope Variable（架构指定） | — | 通过 `@fontsource` 或本地字体引入 |
| **搜索** | **VitePress 内置 LocalSearch** | — | 零配置，客户端索引 50 条数据，无需服务 |
| **图标** | 内联 SVG | — | 避免图标库体积，需求要求"去掉 emoji 用简洁图标" |
| **代码规范** | Prettier（可选） | — | 单人开发可省 |

### 2.2 后端技术栈

**默认方案：零后端。**

需求里唯一涉及"后端"的是两处：

| 需求原文 | 是否真的需要后端 |
|---|---|
| "Top 50 名词的定义和解析（**后端数据库**）" | ❌ 50 条数据用 JSON 文件即可，**不需要数据库** |
| "支持 LLM **在线检索**" | ⚠️ 需要，但走**无服务器函数**即可，不需要常驻服务 |

**因此后端采用"无服务器函数"而非传统服务端：**

| 层 | 选型 | 理由 |
|---|---|---|
| **函数平台** | **Cloudflare Workers**（或 Vercel Functions） | 免费额度足够，**零运维**，无需管理服务器 |
| **LLM 调用** | 直连模型 API（Key 存函数的环境变量） | 避免 Key 暴露在前端 |
| **数据存储** | **项目内 JSON 文件** | 50 条数据，随构建打包，连数据库都不需要 |
| **数据库** | ❌ 不引入 | 数据量小、无写入需求、无多用户状态 |

> **为什么不在前端直连 LLM API**：API Key 会暴露在浏览器里，任何访客都能盗用。
> 必须经一层函数转发。这是**唯一真正需要"后端"的地方**。

### 2.3 部署与运维

| 项 | 选型 | 理由 |
|---|---|---|
| **静态托管** | **GitHub Pages**（首选）/ Vercel | 与现有 GitHub 仓库天然集成，免费 |
| **CI/CD** | **GitHub Actions** | push 即自动构建部署，零配置成本 |
| **域名** | 可选，非必需 | MVP 阶段用 `*.github.io` 子路径即可 |
| **监控** | ❌ 不引入 | MVP 阶段不需要 |

## 三、为什么是 VitePress（核心选型说明）

这是整套方案里**最关键的决策**，单独说明。

### 3.1 候选方案对比

| 方案 | 优势 | 劣势 | 是否适合 |
|---|---|---|---|
| **纯手写 HTML/CSS/JS** | 零依赖、零学习成本 | **50 个名词页要手写 50 遍**，改一次全站样式要改 50 个文件 | ❌ 不可维护 |
| **VitePress** | 文档站专用、Markdown 驱动、内置搜索/TOC | 偏"文档感"，定制视觉需写 CSS | ✅ **推荐** |
| **VuePress** | 生态成熟 | 已被 VitePress 取代，构建慢 | ❌ 过时 |
| **Next.js** | 功能全、生态大 | **过重**，为文档站引入 React + SSR + 一堆概念 | ❌ 杀鸡用牛刀 |
| **Astro** | 内容优先、多框架兼容 | 项目组无经验时学习成本高于 VitePress | ⚠️ 次选 |
| **纯 Markdown + 静态渲染** | 最简 | 无搜索、无 TOC 高亮、无自定义组件 | ❌ 满足不了需求 |

### 3.2 VitePress 恰好命中需求的地方

| 需求 | VitePress 的对应能力 |
|---|---|
| "侧边栏 TOC 固定在左侧" | **内置**侧边栏，配置即得 |
| "当前阅读章节高亮（IntersectionObserver）" | **内置**，开箱即有 |
| "点击章节标题平滑滚动" | **内置** |
| "移动端 TOC 折叠为顶部下拉" | **内置**响应式行为 |
| "搜索 + 分类卡片" | **内置** LocalSearch，零配置 |
| "Wiki 页面不做折叠、连续滚动" | 默认行为，无需配置 |
| "50+ 内容页" | Markdown 文件即页面，**天然支持** |
| "话术区：浅蓝背景卡片 + 复制按钮" | 自定义 Vue 组件，**几十行代码** |
| "右下角回到顶部按钮" | **内置** |

**换句话说**：架构文档里描述的交互细节，VitePress **九成是开箱即用的**。自研反而要重新实现一遍。

### 3.3 需要自己写的部分（工作量评估）

VitePress 覆盖不到、需要自定义的：

| 项 | 实现方式 | 预估工作量 |
|---|---|---|
| 首页四维装备卡 | 自定义 Vue 组件 | 小 |
| 话术卡片 + 复制按钮 | 自定义 Vue 组件 | 小 |
| 名词数据 → 页面生成 | 构建脚本（读 JSON 生成 Markdown） | 中 |
| 色标（🟠🟢🔵 / 🟢🟡🟠🔴） | CSS 类 | 小 |
| 设计规范落地 | CSS 变量文件 | 小 |
| LLM 检索接口 | 无服务器函数 | 中 |

## 四、数据方案：50 词怎么组织

### 4.1 数据文件结构

```
data/
├── terms.json          # 50 个名词的结构化数据
└── categories.json     # 分类定义（解决 9 类 vs 4 层的待裁决项）
```

**terms.json 单条结构**（对应需求 3.2 节的 4 个字段）：

```json
{
  "id": "frontend-backend",
  "name": "前端与后端",
  "nameEn": "Frontend & Backend",
  "category": "web-basics",
  "level": "must-know",
  "oneLine": "前端负责用户看到和操作的部分...",
  "plain": "前端像餐厅前厅，后端像看不见的厨房...",
  "pro": "前端运行在浏览器等客户端...",
  "phrases": [
    "帮我把首页这个页面做出来，数据从后端拿。",
    "前端页面已经做好了，但后端接口还没接上...",
    "这个功能前端显示没问题，但后端返回的数据格式不对..."
  ]
}
```

字段与需求对应：

| 字段 | 对应需求字段 | 说明 |
|---|---|---|
| `name` / `nameEn` | 名词 | 中英文 |
| `oneLine` | 一句话解读 | |
| `plain` | 大白话解读 | |
| `pro` | 专业理解 | 前端折叠展示 |
| `phrases[]` | Vibe 常用话术 | **固定 3 条** |
| `level` | 色标 | `must-know` / `plain` / `pro` → 🟠🟢🔵 |
| `category` | 分类 | ⚠️ **待裁决**：9 类还是 4 层 |

### 4.2 页面生成策略

**推荐：构建期生成，而非运行时渲染。**

```
terms.json  ──构建脚本──▶  50 个 Markdown 文件  ──VitePress──▶  静态 HTML
```

**理由：**
- 构建期生成 → 每词一页是**真静态页**，SEO 好、加载快
- 运行时渲染 → 需要客户端请求数据再渲染，首屏慢，且不利 SEO
- 数据变更只需改 JSON + 重新构建

## 五、样式方案：设计规范如何落地

按需求 6.1 节的设计参数，全部转成 **CSS 变量**：

```css
/* design-tokens.css —— 对应需求 6.1 节 */
:root {
  /* 布局参数（架构文档指定） */
  --sidebar-width: 200px;
  --content-max-width: 680px;

  /* 字体（架构文档指定） */
  --font-heading: 'Manrope Variable', sans-serif;
  --font-heading-weight: 650;      /* wght 650-720 */
  --heading-size-h1: 28px;         /* 字号 22-28px */
  --heading-size-h2: 24px;
  --heading-size-h3: 22px;

  /* 色标（02.创意指定） */
  --tag-must-know: #F59E0B;        /* 必知必会 🟠 */
  --tag-plain: #10B981;            /* 口语化 🟢 */
  --tag-pro: #3B82F6;              /* 专业 🔵 */

  /* 策略梯度（22.架构指定） */
  --level-1: #10B981;              /* 🟢 */
  --level-2: #FBBF24;              /* 🟡 */
  --level-3: #F97316;              /* 🟠 */
  --level-4: #EF4444;              /* 🔴 */
}
```

**不引 UI 组件库的原因**：
- 需求明确"话术区 + 复制按钮"这类组件很少，**自己写比配组件库快**
- 组件库会带来视觉风格约束，与"定制设计规范"冲突
- 新手示例案例，**依赖越少越容易看懂**

## 六、完整技术栈清单

### 6.1 依赖清单

| 类别 | 包名 | 用途 |
|---|---|---|
| 构建 | `vitepress` | 静态站点生成 |
| 构建 | `vue` | 自定义组件（VitePress 已含） |
| 字体 | `@fontsource-variable/manrope` | Manrope Variable 字体 |
| 工具 | `prettier` | 代码格式化（可选） |

**总计 3-4 个依赖。** 无 UI 组件库、无 CSS 框架、无状态管理、无 HTTP 客户端库。

### 6.2 明确不引入的技术

| 技术 | 为什么不用 |
|---|---|
| React / Next.js | 过重，文档站不需要 |
| Tailwind CSS | 需求要"统一设计规范"，CSS 变量更直接 |
| shadcn/ui、Ant Design | 组件需求太少，不值得引入体系 |
| 任何数据库（MySQL/PG/SQLite） | 50 条数据用 JSON |
| 任何后端框架（Express/Nest/Koa） | 只有 LLM 转发一个接口 |
| 状态管理（Pinia/Vuex） | 无跨页状态 |
| TypeScript | 可选，但非必需（数据量小，收益有限） |

## 八、方案轻量度对比

| 维度 | 本方案 | 常规方案 | 差异 |
|---|---|---|---|
| npm 依赖数 | 3-4 个 | 50-200 个 | 数量级差异 |
| 是否需数据库 | ❌ 不需要 | 通常需要 | 省一套运维 |
| 是否需服务器 | ❌ 不需要 | 通常需要 | 省服务器成本 |
| 构建产物 | 纯静态 HTML | 含 JS bundle | 加载更快 |
| 月度成本 | **0 元**（免费额度内） | 服务器费用 | — |
| 学习成本 | 会 Markdown 即可上手 | 需学框架 | 显著低 |
| 部署方式 | push 即部署 | 需配 CI/CD | 配置量小 |

## 十一、风险提示

| 风险 | 说明 | 应对 |
|---|---|---|
| VitePress "文档感"偏强 | 定制成"产品站"视觉需要写 CSS，工作量比预想多 | 提前做视觉稿验证 |
| Wiki 长页体积 | 源文档 700+ 行，单页可能较大 | 构建后实测首屏，必要时懒加载图片 |
| 需求缺口返工 | 分类体系、稳定做 Wiki、陪练 Agent 均未定 | **先定决策再开发** |
| 技术栈与"示例案例"定位的张力 | 若教学价值要求"手写可读"，VitePress 的抽象层反而增加理解成本 | 视教学需求再评估是否降级为纯手写 |
